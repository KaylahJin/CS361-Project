# Data Dictionary: `coop_plans` (V2 – Dynamic Data)

เก็บ "แผนสหกิจศึกษา" ของนักศึกษา 1 แถวต่อ 1 แผน ใช้ข้อมูลร่วมกับ `students`, `positions` (และ `companies`), `periods`

---

## 1. ภาพรวมข้อมูล

ใน V2 ระบบยังไม่มี Login จึง **ไม่มีการตรวจว่าใครเป็นผู้เปลี่ยนสถานะ** ข้อมูลแผนถูกเพิ่มผ่าน Seed/Import หรือ API ที่ยังไม่ผูกกับตัวตนผู้ใช้ สิ่งที่ V2 ต้องรับประกันคือ **ข้อมูลที่เก็บต้องครบและสอดคล้องกัน** และเรียกดู/กรองได้

ลำดับสถานะโดยทั่วไป (ใช้เป็นแนวทางให้ข้อมูลสมเหตุสมผล ยังไม่ถูกบังคับด้วยระบบจนถึง V3)

```
PREPARING ─▶ SUBMITTED ─▶ UNDER_REVIEW ─┬─▶ APPROVED
    ▲                                   ├─▶ REJECTED
    └───────── ส่งกลับแก้ไข ◀────────────┘
```

**ข้อมูลฝั่งนักศึกษาที่ยื่น:** นักศึกษา, รอบเวลา, ตำแหน่ง (ถ้ามี), การรับทราบเงื่อนไข, เวลายอมรับข้อกำหนด, เวลายื่น, หมายเหตุ
**ข้อมูลฝั่งผู้ตรวจรับรอง (อาจารย์/เจ้าหน้าที่):** ชื่อผู้ตรวจ, เวลาตัดสิน, ความเห็น/เหตุผล และสถานะผลลัพธ์

### เหตุผลของการเลือก Data Type

- **`status` เป็น `varchar(20)` + CHECK ไม่ใช้ PostgreSQL ENUM** เพราะ V4 ต้องเพิ่มสถานะ (APPLIED, ACCEPTED, IN_PROGRESS, COMPLETED ตาม FR5) การเพิ่มค่าใน CHECK ง่ายกว่าและย้อนกลับได้ง่ายกว่า ENUM
- **เวลาทั้งหมดเป็น `timestamptz`** เก็บเป็น UTC แสดงผลตามเขตเวลาที่ Frontend (ไทย UTC+7)
- **`acknowledged_pre_course` เป็น boolean** เพราะเป็นการรับทราบแบบใช่/ไม่ใช่ ส่วน **`terms_accepted_at` เป็นเวลา** เพื่อใช้เป็นหลักฐานว่ายอมรับเมื่อไร
- **`reviewer_name` เป็นข้อความ** เพราะ V2 ยังไม่มีตารางผู้ใช้ให้ FK ใน V3 ค่อยเพิ่ม `reviewed_by` ที่อ้างอิงผู้ใช้จริง
- **`student_id`, `period_id`, `position_id` ชนิดตรงกับตารางต้นทาง** (varchar(10)) เพื่อให้ FK ทำงานได้

## 3. สถานะแผน (`status`)

| ค่า | ป้ายแสดงผล (Thai) | ความหมาย | ฟิลด์ที่ควรมีค่าเมื่ออยู่ในสถานะนี้ |
|---|---|---|---|
| `PREPARING` | กำลังเตรียมแผน | ร่างแผน หรือถูกส่งกลับให้แก้ไข | ไม่บังคับ (ถ้าถูกส่งกลับ จะมี `review_comment`) |
| `SUBMITTED` | ยื่นแล้ว รอตรวจ | นักศึกษายื่นแล้ว รอผู้ตรวจรับเรื่อง | `submitted_at`, `terms_accepted_at`, `acknowledged_pre_course = true` |
| `UNDER_REVIEW` | กำลังตรวจสอบ | ผู้ตรวจรับเรื่องและกำลังพิจารณา | เหมือน `SUBMITTED` |
| `APPROVED` | อนุมัติแล้ว | ผ่านการพิจารณา | เหมือน `SUBMITTED` + `reviewer_name`, `reviewed_at` |
| `REJECTED` | ไม่อนุมัติ | ไม่ผ่านการพิจารณา | เหมือน `APPROVED` + `review_comment` (บังคับ) |

**การแทน "ส่งกลับแก้ไข" (FR4):** ชุดสถานะไม่มีค่า RETURNED เอกสารนี้จึงเสนอให้ส่งกลับ = กลับไป `PREPARING` โดยยังเก็บ `review_comment`, `reviewer_name`, `reviewed_at` ของการส่งกลับไว้ ดูหัวข้อ 7 ข้อ 1

## 4. Constraints และ Indexes

**Constraints (ความสอดคล้องของข้อมูล บังคับที่ฐานข้อมูล)**

| ชื่อ | กติกา | ป้องกันปัญหา |
|---|---|---|
| `chk_coop_plans_status` | `status` ต้องเป็นหนึ่งใน 5 ค่าในหัวข้อ 3 | สถานะสะกดผิด/ค่านอกชุด |
| `chk_coop_plans_submitted` | ถ้า `status` ไม่ใช่ `PREPARING` ต้องมี `submitted_at`, `terms_accepted_at` และ `acknowledged_pre_course = true` | แผนที่ยื่นแล้วแต่ไม่มีหลักฐานการยอมรับเงื่อนไข |
| `chk_coop_plans_decision` | ถ้า `status` เป็น `APPROVED` หรือ `REJECTED` ต้องมี `reviewer_name` และ `reviewed_at` | ผลตัดสินที่ไม่รู้ว่าใครตัดสิน |
| `chk_coop_plans_reject_reason` | ถ้า `status = 'REJECTED'` ต้องมี `review_comment` ไม่ว่าง | ปฏิเสธโดยไม่บอกเหตุผล |

กติกาเหล่านี้ตรวจ **ความสอดคล้องของข้อมูล** เท่านั้น ไม่ได้บังคับว่าใครเปลี่ยนสถานะได้หรือเปลี่ยนข้ามลำดับได้หรือไม่ (เรื่องนั้นเป็นของ V3)

**Indexes (รองรับการกรองใน FR8)**

| Index | ใช้กับ |
|---|---|
| `student_id` | แผนของนักศึกษาแต่ละคน, Join กับ `students` |
| (`status`, `submitted_at`) | กรองตามสถานะและเรียงตามเวลายื่น |
| `period_id` | กรองตามรอบเวลา |
| `position_id` | Join ไปยังตำแหน่งและสถานประกอบการ |

## 6. ประเด็นที่ต้องตกลงร่วมกัน (Frontend + Backend + ทีมข้อกำหนด)

| # | ประเด็น | ข้อเสนอในเอกสารนี้ | ทางเลือกอื่น |
|---|---|---|---|
| 1 | "ส่งกลับแก้ไข" แทนด้วยอะไร เพราะชุดสถานะไม่มี RETURNED | กลับไป `PREPARING` + `review_comment` | เพิ่มสถานะ `RETURNED` (แยกชัดกว่า แต่ต้องแก้ CHECK) |
| 2 | `plan_id` ชนิดอะไร | `integer` ที่ระบบสร้าง | `varchar(10)` เหมือนตารางอื่น (เช่น `P001`) ต้องมีตัวสร้างรหัส |
| 3 | `periods` คือรอบรับสมัครหรือขั้นตอนตามกำหนดการ | ตารางนี้อ้างอิง `period_id` ว่าเป็นรอบเวลาของแผน | ถ้า `periods` เป็นขั้นตอน ต้องมีตารางรอบแยก |
| 4 | นักศึกษามีแผนได้กี่แผน | ยังไม่จำกัดใน V2 | จำกัด 1 แผนที่ยังไม่ถูกปฏิเสธ (ทำใน V3 พร้อมกติกา Workflow) |
| 5 | `reviewer_name` เป็นข้อความหรือรอ FK | ข้อความใน V2 | เว้นฟิลด์ไว้เป็น NULL ทั้งหมดจนกว่าจะมีตารางผู้ใช้ |
