# Cooperative Education Planning & Management System V3

เอกสารประกอบการวางแผน V3 แบ่งเป็น Definition, Boundary และโครงสร้าง Issue โดยรวบรวมจากเอกสารนัดประชุมวันที่ 12 ตุลาคม 2569 เวลา 18:00 น. และรายละเอียดที่กำหนดเพิ่มเติมในบทสนทนา

ไฟล์นัดประชุมเป็นชุดคำถามเตรียมการ ส่วนเนื้อหาด้านล่างเป็นข้อกำหนดสำหรับต้นแบบและแผนงานที่เสนอ

## 1. Definition

### Primary User

นักศึกษาที่เตรียมเข้าสู่แผนสหกิจศึกษา โดยเฉพาะชั้นปีที่ 3 ซึ่งต้องตรวจสอบข้อมูล จัดทำแผน ยื่นแผน และติดตามผลการพิจารณา

ผู้ใช้งานที่เกี่ยวข้อง ได้แก่ อาจารย์ที่ปรึกษาและเจ้าหน้าที่สหกิจซึ่งทำหน้าที่ตรวจแผน รวมถึงผู้ดูแลระบบที่จัดการบัญชีและสิทธิ์ผู้ใช้

### Current Situation

V2 รองรับการค้นหาและเรียกดูข้อมูลสหกิจศึกษาจาก Managed Data Source ผู้ใช้ยังยื่นแผนและติดตามผลผ่านเว็บไซต์ไม่ได้

### Problem

นักศึกษายังต้องส่งแผนและติดตามผลผ่านช่องทางอื่น ขณะที่อาจารย์และเจ้าหน้าที่ต้องจัดการเอกสารและแจ้งผลแยกจากเว็บไซต์ ทำให้ข้อมูลแผน ความเห็น และสถานะการพิจารณากระจายอยู่หลายที่

### Desired Outcome

นักศึกษาสามารถเข้าสู่ระบบ บันทึกร่าง และยื่นแผนสหกิจผ่านเว็บไซต์ อาจารย์หรือเจ้าหน้าที่สามารถตรวจและบันทึกผลการพิจารณา นักศึกษาดูสถานะและเหตุผลได้จากแผนเดียวกัน และแก้ไขยื่นใหม่ได้เมื่อแผนถูกส่งกลับ

### Project Vision

เป็นช่องทางกลางสำหรับจัดทำ ยื่น และพิจารณาแผนสหกิจศึกษา โดยผู้ใช้เข้าดูข้อมูลและสถานะได้ผ่านเว็บไซต์ การรับยื่นแผนยังเป็นไปตามช่วงเวลาที่กำหนดของแต่ละรอบ

### V3 Direction

พัฒนาการเข้าสู่ระบบและสิทธิ์ผู้ใช้ ควบคู่กับกระบวนการร่าง ยื่น ตรวจ และแจ้งผลแผนสหกิจ โดยใช้ข้อมูลและโครงสร้างจาก V2 ต่อ

**กระบวนการหลัก:** นักศึกษาเข้าสู่ระบบ → สร้างร่าง → ยื่นแผน → ผู้ตรวจพิจารณา → นักศึกษาดูผลหรือแก้ไขยื่นใหม่

## 2. Boundary

### 2.1 ภายในขอบเขต V3

- การเชื่อมต่อ Cognito เพื่อเข้าสู่ระบบ และการตรวจสิทธิ์ตามบทบาทในแอปพลิเคชัน
- การสร้าง บันทึก และแก้ไขแผนฉบับร่าง รวมถึงการยื่นและยื่นใหม่เมื่อถูกส่งกลับ
- การแสดงรายการแผนและรายละเอียดตามสิทธิ์ของผู้ใช้
- การอนุมัติ ไม่อนุมัติ หรือส่งกลับเพื่อแก้ไขพร้อมความเห็น
- การแสดงสถานะปัจจุบันและข้อมูลผลการพิจารณา ได้แก่ ผู้ตรวจ เวลา และคอมเมนต์
- การเรียกดูประกาศ เกณฑ์ สถานประกอบการ และตำแหน่งงานจากข้อมูลที่มีอยู่
- การนำเข้าข้อมูลนักศึกษาและผลการเรียนแบบ Manual เพื่อใช้ในต้นแบบ

### 2.2 นอกขอบเขต V3

- การเชื่อมต่อ University SSO จริงในรอบนี้ โดยเตรียมแนวทางเพิ่มผ่าน Cognito ในอนาคต
- การดึงข้อมูลเกรดและรายวิชาจากระบบทะเบียนโดยอัตโนมัติ
- การแจ้งเตือนทางอีเมลหรือแชต และ Dashboard วิเคราะห์ขั้นสูง
- การติดตามกระบวนการหลังอนุมัติ เช่น `APPLIED` และ `COMPLETED`
- การเก็บเนื้อหาแผนทุกฉบับเพื่อเปรียบเทียบประวัติการแก้ไขโดยละเอียด
- การเปิดให้สถานประกอบการเข้าระบบเพื่อพิจารณาหรือจัดการแผน

### 2.3 ผู้ใช้งานและสิทธิ์

| ผู้ใช้งาน | ขอบเขตสิทธิ์ |
| --- | --- |
| บุคคลทั่วไป | ดูประกาศ เกณฑ์ และตำแหน่งงานที่กำหนดให้เป็นข้อมูลสาธารณะ |
| นักศึกษา | สร้าง แก้ไข ยื่น และดูผลแผนของตนเองตามสถานะที่อนุญาต |
| อาจารย์ที่ปรึกษา | ดูและพิจารณาแผนของนักศึกษาในความดูแล |
| เจ้าหน้าที่สหกิจ | ดูแผนทั้งหมดในขอบเขตโครงการ และดำเนินการพิจารณาตามกติกาที่กำหนด |
| ผู้ดูแลระบบ | จัดการบัญชี บทบาท การจับคู่บัญชีกับนักศึกษา และความสัมพันธ์อาจารย์ที่ปรึกษา |

สิทธิ์ผู้ดูแลระบบไม่ทำให้มีสิทธิ์อนุมัติแผนโดยอัตโนมัติ การพิจารณาแผนต้องได้รับบทบาทผู้ตรวจด้วย

### 2.4 ระบบภายนอก แหล่งข้อมูล และการไหลของข้อมูล

ในเอกสารนี้ ขอบเขตแอปพลิเคชันครอบคลุมหน้าเว็บ API ตรรกะการทำงาน และฐานข้อมูลของโครงการ ส่วน Cognito แสดงเป็นบริการยืนยันตัวตนภายนอกที่ระบบเชื่อมต่อ

| ผู้เกี่ยวข้องหรือแหล่งข้อมูล | ข้อมูลเข้าสู่ระบบ | ข้อมูลออกจากระบบ |
| --- | --- | --- |
| นักศึกษา | JWT คำค้นหา ข้อมูลแผน และคำขอยื่นแผน | ข้อมูลสหกิจ แผนของตนเอง สถานะ ความเห็น และผลการทำรายการ |
| อาจารย์ / เจ้าหน้าที่ | JWT เงื่อนไขกรองรายการ ผลการพิจารณา และความเห็น | รายการและรายละเอียดแผนตามสิทธิ์ รวมถึงผลการบันทึก |
| Cognito | ผลยืนยันตัวตนและ token ที่แอปใช้เรียก API รวมถึงข้อมูลสำหรับตรวจลายเซ็น token | คำขอเริ่มกระบวนการเข้าสู่ระบบ โดยผู้ใช้ยืนยันตัวตนกับ Cognito |
| ผู้ดูแลและไฟล์ข้อมูลนักศึกษา | ข้อมูลนักศึกษา ผลการเรียน และการมอบหมายอาจารย์ที่ปรึกษา | ผลนำเข้าและรายการข้อมูลที่ผิดพลาด |
| Registry ใน Repository | ข้อมูลสถานประกอบการและตำแหน่งงานที่ทีมปรับปรุง | ผลการนำเข้าหรือปรับปรุงข้อมูล |

ระบบทะเบียนมหาวิทยาลัยไม่มีการรับส่งข้อมูลผ่าน API กับต้นแบบ V3

**แหล่งข้อมูลหลัก (Source of Truth)**

- **Cognito:** บัญชีสำหรับเข้าสู่ระบบและกลุ่มผู้ใช้ที่กำหนดไว้
- **PostgreSQL:** ข้อมูลนักศึกษาที่นำเข้า การจับคู่บัญชี ความสัมพันธ์อาจารย์ที่ปรึกษา แผนสหกิจ และข้อมูลผลการพิจารณา
- **Registry:** ข้อมูลต้นทางของสถานประกอบการและตำแหน่งงานที่ทีมจัดเตรียม

### 2.5 กติกาที่ใช้วางแผนพัฒนาต้นแบบ

- นักศึกษามีแผนที่กำลังดำเนินการได้หนึ่งแผนต่อรอบสหกิจ
- นักศึกษาแก้ไขได้เมื่อแผนเป็นฉบับร่างหรือถูกส่งกลับ ระหว่างรอตรวจให้ระงับการแก้ไข
- การส่งกลับเปิดให้แก้ไขและยื่นใหม่ ส่วนการไม่อนุมัติถือเป็นการสิ้นสุดแผนฉบับนั้น สิทธิ์สร้างแผนใหม่ในรอบเดิมต้องกำหนดเพิ่มเติม
- ผู้ตรวจต้องระบุเหตุผลเมื่อส่งกลับหรือไม่อนุมัติ
- ระบบตรวจเจ้าของแผน สิทธิ์ และสถานะก่อนทำรายการ หากผู้ตรวจดำเนินการพร้อมกัน ต้องป้องกันผลการพิจารณาทับกัน
- เก็บสถานะและข้อมูลผลการพิจารณาที่จำเป็น การเก็บแผนทุกเวอร์ชันยังอยู่นอกขอบเขต

| สถานะที่เสนอ | การดำเนินการที่อนุญาต |
| --- | --- |
| `DRAFT` | นักศึกษาแก้ไขและยื่นแผน |
| `SUBMITTED` | ผู้มีสิทธิ์ตรวจและบันทึกผล |
| `RETURNED` | นักศึกษาแก้ไขและยื่นใหม่ |
| `APPROVED` | ดูผลการอนุมัติ โดยกระบวนการของ V3 สิ้นสุดที่สถานะนี้ |
| `REJECTED` | ดูเหตุผลที่ไม่อนุมัติ โดยกระบวนการของแผนฉบับนี้สิ้นสุดแล้ว |

ชื่อสถานะต้องตรวจให้ตรงกับฐานข้อมูล V2 ก่อนนำไปใช้ หากเปลี่ยนชื่อหรือเพิ่มสถานะ ต้องมีวิธีปรับข้อมูลเดิม

### 2.6 แนวทางสถาปัตยกรรมและสิ่งที่ต้องใช้จาก V2

- **หน้าเว็บ:** React บน S3 และ CloudFront
- **ยืนยันตัวตน:** Cognito User Pool โดย API Gateway ใช้ JWT Authorizer ตรวจ token
- **ประมวลผล:** Lambda ตรวจสิทธิ์ ความครบถ้วนของข้อมูล และเงื่อนไขการเปลี่ยนสถานะ
- **จัดเก็บข้อมูล:** PostgreSQL บน RDS โดยวางแผนเชื่อม Lambda กับ RDS โดยตรงในช่วงต้น และใช้ผลทดสอบประกอบการตัดสินใจเรื่อง RDS Proxy
- **ระบุตัวผู้ใช้:** ใช้ `sub` จาก token ที่ผ่านการตรวจสอบ จับคู่กับข้อมูลผู้ใช้ในฐานข้อมูล แล้วตรวจสิทธิ์ต่อ ไม่ใช้ `student_id` ที่ผู้เรียกส่งมาเป็นหลักฐานระบุตัวตน

V3 ต้องใช้ข้อมูล Company, Position, Period และ Student รวมถึงหน้าแสดงข้อมูล API ฐานข้อมูล และการตั้งค่าบริการที่มีอยู่ใน V2 จึงต้องตรวจโครงสร้างจริงก่อนแก้ไข

### 2.7 ประเด็นที่ยังต้องตรวจสอบ

- เกณฑ์ GPA และรายวิชาที่ใช้จริง รวมถึงระบบจะตรวจเงื่อนไขใดก่อนรับยื่น
- ช่วงรับยื่น จำนวนครั้งที่ยื่นแก้ไข และสิทธิ์สร้างแผนใหม่หลังถูกปฏิเสธ
- แผนต้องผ่านอาจารย์และเจ้าหน้าที่ตามลำดับ หรือผู้ตรวจที่มีสิทธิ์คนใดคนหนึ่งตัดสินได้
- แหล่งข้อมูลนักศึกษาและผลการเรียน ผู้รับผิดชอบนำเข้า และรอบการปรับปรุงข้อมูล
- ความพร้อมของผู้ใช้จริงในการเปลี่ยนมาใช้กระบวนการออนไลน์
- สิทธิ์บริการใน AWS Academy Lab และจำนวนการเชื่อมต่อฐานข้อมูลภายใต้ปริมาณใช้งานที่คาดไว้

ข้อกำหนดที่มีผลต่อการพัฒนาให้บันทึกข้อสรุปหรือสมมติฐานของต้นแบบใน Issue V3-01 ก่อนเริ่มงานที่เกี่ยวข้อง

## 3. โครงสร้าง Issue สำหรับ V3

### 3.1 หลักการแบ่งงาน

- หนึ่ง Issue มีปัญหาหรือผลลัพธ์หลักหนึ่งเรื่อง พร้อมเงื่อนไขตรวจรับที่ชัดเจน
- Issue หลักที่มี Sub-issue ใช้ติดตามภาพรวม และปิดเมื่อ Sub-issue ครบทั้งหมด
- Sub-issue เป็นหน่วยมอบหมายงาน แต่ละรายการต้องทดสอบและตรวจรับได้ตามขอบเขตของตนเอง
- ระบุงานที่ต้องเสร็จก่อนใน `Depends on` งานที่ใช้ฐานข้อมูลหรือ API ร่วมกันต้องอ้างอิงข้อกำหนดชุดเดียวกัน
- การตรวจสิทธิ์และข้อผิดพลาดเป็นส่วนหนึ่งของแต่ละฟังก์ชัน แม้จะมีส่วนตรวจสิทธิ์กลางอยู่แล้ว

รหัสต่อไปนี้ใช้วางแผนงาน ยังไม่ใช่หมายเลข Issue ใน GitHub

**ขอบเขต:** สรุปสิทธิ์และ Workflow จากหัวข้อ 2 ตรวจโครงสร้าง V2 จัดทำแบบฐานข้อมูล API และ Architecture Diagram รวมถึงแนวทางเพิ่ม SSO ผ่าน Cognito ในอนาคต

### 3.2 ลำดับและการตรวจรับงาน

1. เริ่มจาก V3-01 แล้วพัฒนา Cognito และปรับฐานข้อมูลขนานกัน
2. เมื่อมี API และแบบข้อมูลที่ตกลงไว้ สามารถเริ่มหน้าฝั่งนักศึกษาและผู้ตรวจด้วยข้อมูลจำลองได้
3. ก่อนปิดงานแต่ละฟังก์ชัน ต้องเชื่อมกับ API/ฐานข้อมูลจริงและผ่านการตรวจสิทธิ์ตามขอบเขตของงาน
4. งานแสดงสถานะและรายการผู้ตรวจใช้ข้อมูลทดสอบในฐานข้อมูลตรวจรับได้ โดยไม่ต้องรอทุกขั้นตอนของ Workflow จากนั้นทดสอบการเชื่อมต่อครบทั้งระบบใน V3-06.1
5. แต่ละ Issue ที่มอบหมายต้องระบุ `Goal`, `Task`, `Acceptance Criteria`, `Depends on`, `Estimate`, `Assignee` และ `Reviewer` พร้อมแนบหลักฐานผลทดสอบก่อนปิดงาน

การปิด Issue แยกกันหมายถึงงานนั้นมีผลลัพธ์ที่ตรวจรับได้ภายใต้ข้อกำหนดที่ตกลงไว้ งานยังมีความสัมพันธ์กันได้ แต่ต้องไม่เปลี่ยน API หรือโครงสร้างข้อมูลร่วมโดยไม่แจ้งผู้รับผิดชอบงานที่เกี่ยวข้อง
