### V4-01 Student Plan Management — การจัดการแผนของนักศึกษา

**Problem:** นักศึกษาต้องจัดทำและยื่นแผนสหกิจผ่านเว็บไซต์ได้ โดยข้อมูลไม่กระจัดกระจายไปหลายช่องทาง

**Goal:** นักศึกษาสร้างและแก้ไขแผน เลือกหรือเสนอ Employer/Position และยื่นแผนตามเงื่อนไขของระบบได้

**Task**
- สร้างและบันทึกแผนฉบับร่าง
- เปิดแผนเดิมกลับมาแก้ไขได้ตามสถานะที่อนุญาต
- เลือกหรือเสนอ Employer และ Position ตามกติกาที่ทีมตกลง
- ตรวจสอบข้อมูลที่จำเป็นก่อนยื่นแผน
- ตรวจสอบ Period และเงื่อนไขการยื่น
- ส่งแผนเข้าสู่กระบวนการพิจารณา
- ป้องกันการยื่นซ้ำหรือแก้ไขแผนที่ไม่อนุญาต

**Acceptance Criteria**
- [ ] นักศึกษาสร้างแผนและบันทึกร่างได้
- [ ] นักศึกษาเปิดและแก้ไขแผนของตนเองได้ตามสถานะที่อนุญาต
- [ ] เลือกหรือเสนอ Employer และ Position ได้ตามกติกาที่กำหนด
- [ ] ระบบตรวจข้อมูลจำเป็นก่อนยื่นแผน
- [ ] ระบบตรวจสอบช่วงเวลาการยื่นตาม Period
- [ ] เมื่อยื่นสำเร็จ ระบบเปลี่ยนสถานะตาม Workflow
- [ ] ผู้ใช้ไม่สามารถแก้ไขแผนของนักศึกษาคนอื่นได้
- [ ] มีผลทดสอบกรณีสำเร็จ ข้อมูลไม่ครบ และไม่มีสิทธิ์

**Depends on:** ข้อมูล Student, Employer, Position, Period และข้อกำหนด Workflow

**Evidence:** Screenshot การสร้างและยื่นแผน พร้อมผลทดสอบ API

### V4-02 Advisor Review Workflow — กระบวนการตรวจและพิจารณาแผน

**Problem:** อาจารย์ที่ปรึกษาและเจ้าหน้าที่ต้องตรวจแผนและบันทึกผลได้จากระบบเดียวกัน

**Goal:** ผู้ตรวจสามารถเปิดดูแผนที่มีสิทธิ์พิจารณา อนุมัติ หรือส่งกลับพร้อมเหตุผลได้

**Task**
- แสดงรายการแผนที่รอพิจารณา
- เปิดดูรายละเอียดแผน
- ตรวจสอบสิทธิ์ของผู้ตรวจ
- บันทึกผลอนุมัติหรือส่งกลับเพื่อแก้ไข
- บังคับให้ระบุเหตุผลเมื่อส่งกลับ
- รองรับการส่งแผนกลับเข้าสู่กระบวนการพิจารณาหลังแก้ไข
- ป้องกันการบันทึกผลพิจารณาซ้ำหรือพร้อมกันจนข้อมูลทับกัน

**Acceptance Criteria**
- [ ] ผู้ตรวจเห็นเฉพาะแผนที่ตนมีสิทธิ์พิจารณา
- [ ] ผู้ตรวจเปิดดูรายละเอียดแผนได้
- [ ] ผู้ตรวจบันทึกผลอนุมัติหรือส่งกลับได้
- [ ] การส่งกลับต้องมีเหตุผล
- [ ] นักศึกษาสามารถแก้ไขและยื่นใหม่ได้เมื่อถูกส่งกลับ
- [ ] ผู้ไม่มีสิทธิ์ไม่สามารถบันทึกผลพิจารณาได้
- [ ] ระบบตรวจสอบสถานะก่อนบันทึกผล
- [ ] คำขอพร้อมกันไม่ทำให้ผลการพิจารณาทับกัน
- [ ] มีผลทดสอบกรณีสำเร็จและกรณีผิดพลาด

**Depends on:** V4-01 และข้อกำหนด Role/Workflow

**Evidence:** Screenshot หน้าพิจารณาและผลทดสอบ API รวมถึงกรณี Conflict

### V4-03 Plan Status Tracking — การติดตามสถานะแผน

**Problem:** นักศึกษาและผู้เกี่ยวข้องต้องทราบสถานะปัจจุบันของแผนและผลการพิจารณาได้อย่างชัดเจน

**Goal:** แสดงสถานะของแผนอย่างสอดคล้องกันทั้งหน้าเว็บและ API รวมถึงสถานะหลังอนุมัติเมื่อทีมตกลงแล้ว

**Task**
- แสดงสถานะปัจจุบันในหน้ารายการและรายละเอียด
- แสดงข้อมูลผลการพิจารณา เช่น ผู้ตรวจ เวลา และความเห็น
- กำหนดคำแสดงผลสถานะให้ตรงกับระบบ
- พิจารณารองรับ Applied, Accepted, In Progress และ Completed
- กำหนดสิทธิ์ผู้เปลี่ยนสถานะหลังอนุมัติ

**Acceptance Criteria**
- [ ] ผู้ใช้เห็นสถานะล่าสุดของแผนที่ตนมีสิทธิ์ดู
- [ ] สถานะที่แสดงตรงกับข้อมูล API/Database
- [ ] แสดงผลการพิจารณาและความเห็นที่เกี่ยวข้อง
- [ ] ไม่แสดงสถานะที่ทีมยังไม่ได้ตกลงหรือระบบยังไม่รองรับ
- [ ] การเปลี่ยนสถานะเป็นไปตามสิทธิ์และ Workflow
- [ ] มีผลทดสอบการแสดงผลและการเปลี่ยนสถานะ

**Depends on:** V4-01 และ V4-02

**Open Decision:** ทีมต้องตกลงว่าจะใช้สถานะ Applied, Accepted, In Progress และ Completed ทั้งหมดหรือไม่ รวมถึงใครมีสิทธิ์เปลี่ยนสถานะเหล่านี้

**Evidence:** Screenshot หน้ารายการและรายละเอียดแผน พร้อมผลทดสอบสถานะ

### V4-04 Deadline Management — การจัดการกำหนดเวลา

**Problem:** ผู้ใช้ต้องทราบว่าแผนใกล้ถึงกำหนดหรือเลยกำหนดแล้ว เพื่อจัดลำดับการดำเนินงานได้

**Goal:** แสดง Deadline และจำแนกเป็น Upcoming, Near Deadline, Overdue และ No Deadline

**Task**
- แสดงวันและเวลาสิ้นสุดของ Period หรือกำหนดส่งที่เกี่ยวข้อง
- คำนวณสถานะกำหนดเวลาจากวันที่ปัจจุบัน
- แสดง Upcoming
- แสดง Near Deadline
- แสดง Overdue
- จัดการกรณีไม่มี Deadline
- ใช้กติกาการคำนวณเดียวกันระหว่าง API และหน้าเว็บ

**Acceptance Criteria**
- [ ] แสดง Deadline ได้ถูกต้อง
- [ ] จำแนก Upcoming, Near Deadline, Overdue และ No Deadline ได้
- [ ] Near Deadline ใช้ Threshold ที่ทีมตกลง
- [ ] กรณีไม่มี Deadline ไม่ถูกแสดงเป็น Overdue
- [ ] รองรับ Timezone อย่างถูกต้อง
- [ ] มีผลทดสอบก่อนถึงกำหนด ใกล้ถึงกำหนด เลยกำหนด และไม่มีวันกำหนด

**Depends on:** ข้อมูล Period/Deadline และข้อสรุป Near Deadline Threshold

**Open Decision:** Near Deadline หมายถึงก่อนกำหนดกี่วันหรือกี่ชั่วโมง และใช้ Timezone ใด

**Evidence:** Screenshot แต่ละสถานะ พร้อมผลทดสอบขอบเขตวันที่และเวลา

### V4-05 Search, Filter & Access Control — การค้นหา กรอง และควบคุมสิทธิ์

**Problem:** ผู้ใช้ต้องค้นหาแผนที่เกี่ยวข้องได้สะดวก และต้องไม่สามารถเข้าถึงข้อมูลที่เกินสิทธิ์ของตนเอง

**Goal:** ค้นหาและกรองแผนตาม Student, Employer, Period และ Status พร้อมตรวจสอบสิทธิ์ตาม Role

**Task**
- ค้นหาและกรองตาม Student
- ค้นหาและกรองตาม Employer
- ค้นหาและกรองตาม Period
- ค้นหาและกรองตาม Status
- จำกัดรายการและรายละเอียดตาม Role
- ตรวจสิทธิ์ที่ API ทุกครั้ง
- บันทึกการเปลี่ยนแปลงสำคัญเพื่อ Audit เฉพาะส่วนที่ทีมตกลงและมีข้อมูลรองรับ

**Acceptance Criteria**
- [ ] ตัวกรอง Student ทำงานได้
- [ ] ตัวกรอง Employer ทำงานได้
- [ ] ตัวกรอง Period ทำงานได้
- [ ] ตัวกรอง Status ทำงานได้
- [ ] ผู้ใช้เห็นข้อมูลตาม Role ของตนเอง
- [ ] API ปฏิเสธคำขอที่ไม่มีสิทธิ์ แม้เรียก API โดยตรง
- [ ] ตรวจสิทธิ์ทั้งการอ่านและการแก้ไข/พิจารณาตาม Role
- [ ] จัดการกรณีไม่มีผลลัพธ์และค่าตัวกรองไม่ถูกต้อง
- [ ] มีผลทดสอบแยกตาม Role และตัวกรอง

**Depends on:** ข้อมูลแผน Student Employer Period Status และข้อกำหนด Role/Permission

**Open Decision:** ทีมต้องตกลงความหมายของตัวกรองแต่ละประเภท การค้นหาแบบ Exact/Partial และขอบเขตข้อมูลที่แต่ละ Role มองเห็น

**Evidence:** Screenshot ตัวกรองและผลทดสอบ API/Role Permission
