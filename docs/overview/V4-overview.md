# V4: Planning, Tracking & Reliability — Overview

## 1. Overview

V4 มีเป้าหมายในการพัฒนาระบบ Cooperative Education Planning & Management System จาก V3 ให้รองรับการวางแผนและติดตามนักศึกษาและแผนสหกิจศึกษาได้อย่างเป็นระบบ โดยครอบคลุมหลายสถานะ หลายรอบเวลา และหลายสถานประกอบการ รวมถึงการจัดการกำหนดเวลา (Deadline) และการบันทึกประวัติการเปลี่ยนแปลงข้อมูล (Activity History)

นอกจากนี้ ระบบต้องช่วยลดความเสี่ยงจากข้อมูลตกหล่นหรือสถานะไม่สอดคล้องกัน และคำนึงถึงความน่าเชื่อถือและความพร้อมใช้งานของระบบ (Reliability & Availability)

V4 จะพัฒนาต่อยอดจากระบบ V3 ที่มีอยู่ โดยนำความสามารถและโครงสร้างพื้นฐานเดิมกลับมาใช้ให้มากที่สุด หลีกเลี่ยงการสร้างระบบพื้นฐานที่มีอยู่แล้วขึ้นมาใหม่ และต้องไม่ทำให้ Workflow เดิมของ V3 เสียหาย

## 2. Problem / Goal

### Problem

การจัดการข้อมูลสหกิจศึกษามีข้อมูลที่เกี่ยวข้องหลายส่วน เช่น นักศึกษา แผนสหกิจศึกษา รอบเวลาการออกสหกิจ และสถานประกอบการ หากไม่มีระบบติดตามที่ชัดเจนอาจเกิดปัญหา เช่น

- ไม่สามารถติดตามสถานะของนักศึกษาหรือแผนสหกิจศึกษาได้ครบถ้วน
- จัดการข้อมูลที่เกี่ยวข้องกับหลายรอบเวลาหรือหลายสถานประกอบการได้ไม่สะดวก
- ผู้ใช้งานอาจพลาดกำหนดเวลาสำคัญ (Deadline)
- ไม่สามารถตรวจสอบย้อนหลังได้ว่าข้อมูลหรือสถานะมีการเปลี่ยนแปลงอย่างไร
- ข้อมูลตกหล่นหรือสถานะของข้อมูลไม่สอดคล้องกัน
- ระบบอาจเกิดข้อผิดพลาดหรือไม่พร้อมใช้งานระหว่างการดำเนินงาน

### Goals

V4 มีเป้าหมายดังนี้

1. รองรับการติดตามนักศึกษาและแผนสหกิจศึกษาในหลายสถานะ
2. รองรับข้อมูลที่เกี่ยวข้องกับหลายรอบเวลาการออกสหกิจศึกษา
3. รองรับการจัดการข้อมูลที่เกี่ยวข้องกับหลายสถานประกอบการ
4. รองรับการกำหนดและติดตาม Deadline ที่เกี่ยวข้อง
5. บันทึกประวัติการเปลี่ยนแปลงเพื่อให้ตรวจสอบย้อนหลังได้
6. ลดความเสี่ยงจากข้อมูลตกหล่นและสถานะไม่สอดคล้องกัน
7. พิจารณาความน่าเชื่อถือและความพร้อมใช้งานของระบบ

## 3. Scope

### In Scope

**3.1 Student & Plan Status Tracking**

- รองรับการติดตามสถานะของนักศึกษาและแผนสหกิจศึกษา
- สามารถตรวจสอบสถานะปัจจุบันของข้อมูลได้
- การเปลี่ยนสถานะต้องเป็นไปตามเงื่อนไขและสิทธิ์ของผู้ใช้งาน
- ต้องรักษา Workflow เดิมของ V3 และไม่เพิ่มสถานะใหม่โดยไม่มีข้อสรุปจากทีม

**3.2 Multiple Period & Employer Management**

- รองรับข้อมูลนักศึกษาที่เกี่ยวข้องกับหลายรอบเวลาการออกสหกิจศึกษา
- รองรับการค้นหาและจัดการข้อมูลสถานประกอบการที่เกี่ยวข้องกับแผน
- สามารถแยกแยะข้อมูลตามรอบเวลาและสถานประกอบการได้อย่างถูกต้อง
- รูปแบบการเลือกหรือเชื่อมโยงหลายสถานประกอบการต้องเป็นไปตามข้อสรุปของทีม

**3.3 Deadline Management**

- รองรับการกำหนดและจัดเก็บ Deadline ที่เกี่ยวข้องกับการดำเนินงานสหกิจศึกษา
- ผู้ใช้งานสามารถตรวจสอบกำหนดเวลาที่เกี่ยวข้องได้
- ข้อมูล Deadline ต้องสอดคล้องกับรอบเวลาและกระบวนการที่เกี่ยวข้อง
- การกำหนดสิทธิ์ในการสร้างหรือแก้ไข Deadline ต้องเป็นไปตามบทบาทที่ทีมกำหนด

**3.4 Activity History**

- บันทึกประวัติการเปลี่ยนแปลงข้อมูลที่สำคัญ
- สามารถตรวจสอบผู้ดำเนินการและเวลาที่เกิดการเปลี่ยนแปลงได้
- ประวัติต้องสอดคล้องกับการเปลี่ยนแปลงที่เกิดขึ้นจริง
- ใช้ประวัติในการตรวจสอบย้อนหลังเมื่อเกิดปัญหาด้านข้อมูลหรือสถานะ

**3.5 Reliability & Availability**

- ตรวจสอบความถูกต้องและความสอดคล้องของข้อมูล
- ป้องกันการเปลี่ยนสถานะที่ไม่ถูกต้องตามเงื่อนไข
- ป้องกันการดำเนินการซ้ำหรือการเขียนทับข้อมูลที่ไม่ถูกต้อง
- รองรับการจัดการข้อผิดพลาดจาก API และ Backend
- ทดสอบความพร้อมใช้งานและการกลับมาทำงานหลังเกิดข้อผิดพลาดตามขอบเขตที่กำหนด

**3.6 Integration & Testing**

- ทดสอบการทำงานร่วมกับความสามารถเดิมของ V3
- ทดสอบสถานการณ์การใช้งานตาม TC1 และ TC2
- ทดสอบ Regression ของกติกาสำคัญใน V3
- ตรวจสอบว่าการพัฒนาของ V4 ไม่ทำให้ความสามารถเดิมเสียหาย

### Out of Scope

- การสร้างระบบ Login และ Authentication ใหม่
- การสร้างระบบ Role-Based Access Control (RBAC) ใหม่ทั้งหมด
- การเขียนระบบสร้าง ส่ง ตรวจสอบ และส่งกลับแผนสหกิจศึกษาของ V3 ใหม่ทั้งหมด
- การเชื่อมต่อกับระบบภายนอกที่ไม่ได้ระบุใน Requirement
- การพัฒนาระบบแจ้งเตือนผ่าน Email, SMS หรือช่องทางภายนอกโดยอัตโนมัติ
- การพัฒนาระบบ Dashboard หรือ Analytics ขั้นสูงที่ไม่จำเป็นต่อ Requirement
- การสร้างระบบใหม่ทั้งหมดแทนการต่อยอดจาก V3

## 4. Existing System & Architecture

### 4.1 Existing V3 Architecture

ระบบ V3 มีองค์ประกอบหลักตามสถาปัตยกรรมที่ใช้ในโครงการ ได้แก่

- **Frontend:** React และ TypeScript
- **Authentication:** Amazon Cognito
- **API:** Amazon API Gateway
- **Backend:** AWS Lambda
- **Database:** PostgreSQL บน Amazon RDS
- **Authorization:** การตรวจสอบสิทธิ์ตาม Role และเงื่อนไขของระบบ

องค์ประกอบข้างต้นเป็นสถาปัตยกรรมของระบบ V3 ที่โครงการพัฒนามาแล้ว ไม่ได้หมายความว่าความสามารถใหม่ทั้งหมดของ V4 ได้ติดตั้งหรือเปิดใช้งานแล้ว

ก่อนพัฒนา V4 ต้องตรวจสอบโค้ด ฐานข้อมูล API และ Infrastructure ปัจจุบัน เพื่อยืนยันความสามารถที่มีอยู่จริง รวมถึงตรวจสอบข้อจำกัดของแต่ละส่วน

### 4.2 V4 Proposed Architecture & Integration

V4 เสนอให้พัฒนาต่อยอดบนสถาปัตยกรรมเดิมของ V3 โดยพิจารณาการเพิ่มหรือปรับปรุงองค์ประกอบต่อไปนี้ตาม Requirement และผลการตรวจสอบระบบ

- **Frontend:** เพิ่มหน้าหรือส่วนแสดงผลสำหรับติดตามสถานะ รอบเวลา Deadline และประวัติการเปลี่ยนแปลง
- **API / Backend:** เพิ่มหรือปรับปรุง API สำหรับการติดตามข้อมูล การจัดการ Deadline และการอ่านประวัติ
- **Database:** ปรับปรุง Schema หรือเพิ่มตารางเท่าที่จำเป็นสำหรับข้อมูลที่ V4 ต้องรองรับ
- **Authorization:** ใช้ระบบสิทธิ์เดิม และตรวจสอบสิทธิ์ของผู้ใช้งานในแต่ละการดำเนินการ
- **Reliability:** เพิ่มการตรวจสอบความถูกต้อง การจัดการข้อผิดพลาด และการป้องกันข้อมูลไม่สอดคล้องกันตามขอบเขตงาน

รายการเหล่านี้เป็นแนวทางการพัฒนาที่เสนอไว้ ไม่ใช่รายการยืนยันว่าพัฒนาเสร็จแล้ว การตัดสินใจเปลี่ยนแปลงจริงต้องผ่านการตรวจสอบระบบ V3 และข้อตกลงของทีมก่อน

## 5. User Scenarios & Acceptance Testing

V4 ต้องรองรับการทดสอบตามสถานการณ์การใช้งานที่กำหนดไว้ โดย TC1 และ TC2 เป็นสถานการณ์ทดสอบหลัก

### TC1: อาจารย์ที่ปรึกษาสหกิจศึกษา

**Scenario:** อาจารย์ที่ปรึกษาได้รับมอบหมายให้ตรวจสอบแผนสหกิจศึกษาของนักศึกษา

**Steps:**

1. อาจารย์เข้าสู่ระบบด้วยบัญชีที่มีสิทธิ์เป็นอาจารย์ที่ปรึกษา
2. ค้นหาแผนสหกิจศึกษาของนักศึกษาที่ได้รับมอบหมาย
3. เปิดดูรายละเอียดของแผน
4. แสดงความคิดเห็นและส่งแผนกลับให้นักศึกษาแก้ไข
5. นักศึกษาเข้าสู่ระบบและแก้ไขข้อมูลตามความคิดเห็น
6. นักศึกษาส่งแผนกลับเข้ามาเพื่อให้อาจารย์ตรวจสอบอีกครั้ง
7. ตรวจสอบว่าแผนกลับเข้าสู่กระบวนการตรวจสอบได้อย่างถูกต้อง

**Expected Result:**

- อาจารย์สามารถค้นหาและตรวจสอบแผนของนักศึกษาที่ได้รับมอบหมายได้
- อาจารย์ไม่สามารถดำเนินการพิจารณาแผนของนักศึกษาที่ไม่ได้รับมอบหมาย
- อาจารย์สามารถแสดงความคิดเห็นและส่งแผนกลับเพื่อแก้ไขได้
- นักศึกษาสามารถแก้ไขและส่งแผนอีกครั้งได้ตาม Workflow ของ V3
- สถานะของแผนถูกต้องตามกระบวนการ
- สามารถตรวจสอบประวัติการเปลี่ยนแปลงที่เกี่ยวข้องได้

### TC2: นักศึกษา

**Scenario:** นักศึกษากำลังเตรียมตัวสำหรับการออกสหกิจศึกษาในภาคการศึกษาถัดไป

**Steps:**

1. นักศึกษาเข้าสู่ระบบ
2. ค้นหาสถานประกอบการที่สนใจ
3. ค้นหารอบเวลาการออกสหกิจศึกษาที่เกี่ยวข้อง
4. สร้างแผนสหกิจศึกษาของตนเอง
5. เลือกสถานประกอบการและตำแหน่งที่ต้องการ หรือเสนอข้อมูลสถานประกอบการตามความสามารถของระบบ
6. ส่งแผนเพื่อให้อาจารย์ที่ปรึกษาตรวจสอบ
7. ตรวจสอบสถานะปัจจุบันของแผน

**Expected Result:**

- นักศึกษาสามารถค้นหาสถานประกอบการและรอบเวลาที่เกี่ยวข้องได้
- นักศึกษาสามารถสร้างแผนของตนเองได้
- นักศึกษาสามารถเลือกหรือเสนอข้อมูลสถานประกอบการได้ตาม Workflow ที่ระบบรองรับ
- นักศึกษาสามารถส่งแผนให้อาจารย์ตรวจสอบได้
- ระบบแสดงสถานะปัจจุบันของแผนได้ถูกต้อง
- ระบบไม่สร้างแผนซ้ำหรือเชื่อมโยงข้อมูลผิดรอบเวลา

### 5.3 V3 Regression Test Cases

นอกจาก TC1 และ TC2 ต้องทดสอบกติกาสำคัญของ V3 เพื่อยืนยันว่าการพัฒนา V4 ไม่ทำให้ Workflow และการควบคุมข้อมูลเดิมเสียหาย

| Test Case | Test Scenario | Expected Result |
|---|---|---|
| RT1: Advisor Assignment Authorization | Advisor พยายามเปิดดูหรือพิจารณาแผนของนักศึกษาที่ไม่ได้รับมอบหมาย | ระบบปฏิเสธการเข้าถึงหรือดำเนินการ และไม่เปลี่ยนแปลงข้อมูล |
| RT2: Review Comment Validation | Reviewer เลือก RETURNED หรือ REJECTED โดยไม่ระบุเหตุผล | ระบบปฏิเสธคำขอ และไม่เปลี่ยนสถานะของแผน |
| RT3: One Active Plan per Period | นักศึกษาพยายามสร้างแผนที่ยังดำเนินการอยู่ซ้ำในรอบเวลาเดียวกัน | ระบบปฏิเสธการสร้างแผนซ้ำ โดยไม่กระทบแผนเดิม |
| RT4: Review Status Validation | ผู้ใช้งานพยายามพิจารณาแผนที่ไม่ได้อยู่ในสถานะที่อนุญาตให้พิจารณา | ระบบปฏิเสธการดำเนินการ และสถานะเดิมไม่เปลี่ยนแปลง |
| RT5: Concurrent Review Protection | ผู้ใช้งานสองคนพยายามพิจารณาแผนเดียวกันในเวลาใกล้เคียงกัน หรือมีการส่งคำขอโดยใช้ข้อมูลสถานะเก่า | ระบบยอมรับการเปลี่ยนแปลงที่ถูกต้องเพียงรายการเดียว และคำขอที่ขัดแย้งได้รับ HTTP 409 Conflict โดยไม่เขียนทับผลพิจารณาเดิม |

**Regression Test Conditions:**

- การทดสอบต้องใช้บัญชีและข้อมูลที่มีสิทธิ์หรือสถานะตรงกับแต่ละกรณี
- ต้องตรวจสอบทั้งผลลัพธ์จาก API และข้อมูลที่ถูกบันทึกในฐานข้อมูลตามความเหมาะสม
- กรณีที่ระบบปฏิเสธคำขอต้องยืนยันว่าไม่มีการเปลี่ยนแปลงข้อมูลที่ไม่ถูกต้อง
- ต้องเก็บผลการทดสอบหรือหลักฐานที่ตรวจสอบย้อนหลังได้
- หากพบว่าพฤติกรรมของ V3 ในระบบจริงแตกต่างจากเงื่อนไขที่ระบุ ต้องตรวจสอบเอกสาร API และ Workflow ก่อนปรับ Expected Result โดยไม่เปลี่ยนกติกาเอง

### 5.4 Additional Reliability Tests

นอกจาก TC1, TC2 และ Regression Tests ต้องทดสอบเพิ่มเติมในประเด็นต่อไปนี้

- การเปลี่ยนสถานะที่ไม่ถูกต้องตามเงื่อนไขของระบบ
- ความถูกต้องของข้อมูลเมื่อมีการแก้ไขหรือดำเนินการซ้ำ
- การป้องกันข้อมูลตกหล่นหรือสถานะไม่สอดคล้องกัน
- การบันทึกและตรวจสอบประวัติการเปลี่ยนแปลง
- การทำงานของระบบเมื่อ API หรือ Backend เกิดข้อผิดพลาด
- ความพร้อมใช้งานของระบบและการกลับมาทำงานได้หลังเกิดข้อผิดพลาดตามขอบเขตที่ทดสอบได้

## 7. Open Decisions

ประเด็นต่อไปนี้ยังต้องตรวจสอบระบบ V3 และหารือร่วมกันในทีมก่อนกำหนดเป็นข้อสรุปของการพัฒนา

1. **Status Model:** ต้องมีสถานะใดเพิ่มเติมจากสถานะที่มีอยู่ใน V3 หรือไม่ และสถานะของนักศึกษากับแผนควรแยกจากกันอย่างไร
2. **Multiple Employers:** การรองรับหลายสถานประกอบการควรเป็นการเลือกหลายแห่งในแผนเดียว หรือเป็นข้อมูลการสมัครหรือแผนแยกกัน
3. **Multiple Periods:** นักศึกษาสามารถมีแผนในหลายรอบเวลาได้อย่างไร และมีข้อจำกัดต่อหนึ่งรอบเวลาหรือไม่
4. **Deadline Ownership:** ใครเป็นผู้กำหนดและแก้ไข Deadline และ Deadline แต่ละประเภทมีผลกับผู้ใช้งานกลุ่มใด
5. **Activity History:** ต้องบันทึกเฉพาะการเปลี่ยนสถานะ หรือรวมถึงการแก้ไขข้อมูลสำคัญอื่น ๆ ด้วย
6. **Availability Scope:** จะใช้วิธีใดในการตรวจสอบความพร้อมใช้งานของระบบให้เหมาะสมกับเวลาและทรัพยากรที่มี

การตัดสินใจในหัวข้อเหล่านี้ต้องอ้างอิงความสามารถเดิมของ V3 และ Requirement ของ V4 เพื่อหลีกเลี่ยงการเพิ่มขอบเขตงานที่ไม่จำเป็น

## 8. Success Criteria

ถือว่า V4 บรรลุเป้าหมายเมื่อ

- ระบบสามารถติดตามนักศึกษาและแผนสหกิจศึกษาในหลายสถานะได้อย่างถูกต้อง
- ระบบรองรับข้อมูลหลายรอบเวลาและหลายสถานประกอบการตามขอบเขตที่ทีมกำหนด
- ผู้ใช้งานสามารถตรวจสอบ Deadline ที่เกี่ยวข้องได้
- ระบบบันทึกประวัติการเปลี่ยนแปลงที่สำคัญและตรวจสอบย้อนหลังได้
- ระบบลดความเสี่ยงจากข้อมูลตกหล่นและสถานะไม่สอดคล้องกัน
- ระบบผ่านการทดสอบความถูกต้องและความพร้อมใช้งานตามขอบเขตที่กำหนด
- TC1 และ TC2 ผ่านการทดสอบตาม Expected Result
- Regression Tests RT1–RT5 ผ่านตาม Expected Result
- ความสามารถเดิมของ V3 ที่เกี่ยวข้องยังทำงานได้หลังการพัฒนา V4
- มีหลักฐานผลการทดสอบที่สามารถตรวจสอบย้อนหลังได้

## 9. Development Constraints

- พัฒนาต่อยอดจาก V3 โดยนำ Code, Database, API และ Infrastructure เดิมกลับมาใช้ให้มากที่สุด
- หลีกเลี่ยงการเปลี่ยนแปลง Workflow เดิมโดยไม่มีเหตุผลจาก Requirement
- ตรวจสอบผลกระทบต่อข้อมูลเดิมก่อนแก้ไข Database Schema
- แยกความสามารถที่ติดตั้งใช้งานแล้วออกจากแนวทางที่เสนอหรือสิ่งที่ยังไม่ได้พัฒนาให้ชัดเจน
- ทุก Issue ต้องมี Acceptance Criteria และหลักฐานการทดสอบ
- การเปลี่ยนแปลงสิทธิ์และสถานะต้องสอดคล้องกับกติกาเดิมของ V3 หรือข้อสรุปที่ทีมอนุมัติ
- ให้ความสำคัญกับความถูกต้องของข้อมูลและการทำงานร่วมกันระหว่างสมาชิก
- พิจารณาขอบเขตงานให้เหมาะสมกับระยะเวลาการพัฒนาและทรัพยากรของทีม
