# V4: Planning, Tracking & Reliability --- Overview

## 1. Overview

V4 ต่อยอดระบบ Cooperative Education Planning & Management System จาก V3
เพื่อให้การวางแผนและติดตามนักศึกษา/แผนสหกิจศึกษามีความชัดเจน ตรวจสอบได้
และลดความเสี่ยงจากข้อมูลตกหล่นหรือสถานะไม่สอดคล้องกัน โดยให้ความสำคัญกับ 2
สถานการณ์หลัก ได้แก่

-   **TC1 --- Advisor Review & Resubmission:** อาจารย์ที่ปรึกษาตรวจสอบแผน
    ส่งกลับให้นักศึกษาแก้ไข และตรวจสอบแผนที่ส่งกลับเข้ามาใหม่
-   **TC2 --- Student Plan Creation & Tracking:**
    นักศึกษาค้นหาสถานประกอบการและรอบเวลาที่เกี่ยวข้อง สร้างแผนของตนเอง
    ส่งให้อาจารย์ตรวจสอบ และติดตามสถานะ

V4 จะนำระบบ Login, Role, Workflow และ Infrastructure ของ V3
กลับมาใช้ให้มากที่สุด ไม่สร้างระบบพื้นฐานเดิมขึ้นใหม่ และต้องไม่ทำให้กติกาและ Workflow
เดิมของ V3 เสียหาย

ขอบเขตฉบับนี้กำหนดให้เหมาะกับเวลาพัฒนา โดยแยกสิ่งที่ทำใน V4
ออกจากข้อเสนอสำหรับรุ่นถัดไปอย่างชัดเจน

## 2. Problem / Goal

### Problem

การดำเนินงานสหกิจศึกษาเกี่ยวข้องกับนักศึกษา แผนสหกิจศึกษา รอบเวลาการออกสหกิจศึกษา
สถานประกอบการ และการพิจารณาของอาจารย์ หากติดตามข้อมูลไม่ชัดเจนอาจเกิดปัญหา เช่น

-   นักศึกษาและอาจารย์ไม่เห็นสถานะปัจจุบันหรือขั้นตอนถัดไปอย่างชัดเจน
-   การส่งแผนกลับเพื่อแก้ไขและส่งใหม่อาจติดตามต่อได้ยาก
-   ผู้ใช้อาจพลาดกำหนดเวลาที่มีอยู่ในระบบ
-   ตรวจสอบย้อนหลังได้ยากว่าแผนเปลี่ยนสถานะหรือถูกดำเนินการเมื่อใด
-   การดำเนินการซ้ำหรือคำขอที่ขัดแย้งกันอาจทำให้ข้อมูลไม่สอดคล้องกัน
-   ระบบอาจเกิดข้อผิดพลาดหรือไม่พร้อมใช้งานระหว่างดำเนินงาน

### Goals

1.  รองรับการทำงานตามสถานการณ์ TC1 และ TC2 ได้ครบตาม Expected Result
2.  แสดงสถานะของแผนและติดตามการส่งกลับ/ส่งใหม่ได้ถูกต้องตาม Workflow ของ V3
3.  ใช้ข้อมูลสถานประกอบการและรอบเวลาที่ระบบ V3 มีอยู่
    โดยจำกัดหนึ่งสถานประกอบการต่อหนึ่งแผนในขอบเขต V4
4.  แสดง Deadline ที่มีอยู่แล้วในระบบ หากตรวจสอบพบแหล่งข้อมูลที่ใช้งานได้
5.  ตรวจสอบประวัติการดำเนินการที่จำเป็นเท่าที่ระบบปัจจุบันรองรับและเวลาพัฒนาเอื้ออำนวย
6.  ทดสอบความถูกต้อง การจัดการข้อผิดพลาด และการทำงานร่วมกับ V3
7.  ตรวจสอบและนำเสนอ Network Architecture / การเชื่อมต่อ RDS
    โดยอ้างอิงการตั้งค่าจริง
    ไม่กล่าวอ้างว่าสภาพแวดล้อมปลอดภัยหรือพร้อมใช้งานหากยังไม่ได้ตรวจสอบ

## 3. Scope

### In Scope

**3.1 Student & Plan Status Tracking** -
ทำให้ผู้ใช้ตรวจสอบสถานะปัจจุบันของแผนได้ - รองรับการสร้าง ส่ง ตรวจสอบ ส่งกลับแก้ไข
และส่งใหม่ตาม Workflow ที่มีใน V3 -
การเปลี่ยนสถานะต้องผ่านการตรวจสอบสิทธิ์และเงื่อนไขฝั่ง Backend -
ไม่เพิ่มชื่อสถานะหรือเปลี่ยน State Model ของ V3 โดยไม่มีข้อสรุปจากทีม

**3.2 Student Plan Flow** - นักศึกษาค้นหาสถานประกอบการ/ตำแหน่งงานที่ระบบมี
และเลือกรอบเวลาที่มีอยู่ - V4 กำหนดขอบเขตเบื้องต้นเป็น
**หนึ่งสถานประกอบการต่อหนึ่งแผน** - ใช้ Period ที่ V3 รองรับอยู่แล้ว ไม่สร้างระบบจัดการ
Period ใหม่ - รักษาข้อจำกัดเดิม เช่น หนึ่งแผนที่ยังดำเนินการอยู่ต่อนักศึกษาต่อหนึ่ง Period
ตามกติกา V3

**3.3 Deadline Display** - แสดง Deadline ที่มีอยู่แล้วและเกี่ยวข้องกับ
Period/กระบวนการ หากตรวจสอบพบแหล่งข้อมูลที่เชื่อถือได้ - ขอบเขต V4
เป็นการแสดงผลเท่านั้น ไม่สร้างระบบกำหนด/แก้ไข Deadline ใหม่ -
ไม่เพิ่มการแจ้งเตือนอัตโนมัติผ่าน Email, SMS หรือช่องทางภายนอก

**3.4 Activity History (Limited)** -
ตรวจสอบว่าระบบมีข้อมูลประวัติหรือข้อมูลเวลาที่จำเป็นอยู่แล้วหรือไม่ -
หากทำได้ภายในเวลาที่กำหนด ให้แสดงเหตุการณ์สำคัญที่จำเป็นต่อ TC1 เช่น การส่งแผน
การส่งกลับ และการส่งใหม่ - ไม่ถือว่าเป็น Full Audit Log;
ห้ามแสดงผู้ดำเนินการหรือเวลาที่ไม่มีข้อมูลยืนยัน - หากต้องเพิ่ม Schema/ตาราง
ต้องตกลงกับทีมและประเมินผลกระทบก่อน

**3.5 Reliability & Regression** -
ตรวจสอบการเปลี่ยนสถานะที่ไม่ถูกต้องและการดำเนินการซ้ำ - จัดการ API/Backend errors
โดยไม่ทำให้ข้อมูลเปลี่ยนแปลงผิดพลาด - ทดสอบ TC1, TC2 และ Regression Test
RT1--RT5 - บันทึกผลและหลักฐานจริง รวมถึงกรณีที่ไม่ได้ทดสอบ

**3.6 AWS Networking & RDS Review** - ตรวจสอบ VPC, Subnets, Route
Tables, Security Groups, Lambda VPC Configuration, RDS Subnet Group
และค่า Publicly Accessible จาก AWS/Terraform ที่เข้าถึงได้ - จัดทำ Network
Architecture Diagram ให้ตรงกับสภาพแวดล้อมจริง - ระบุความแตกต่างระหว่าง Current
State กับ Recommended Target State - การเปลี่ยน RDS เป็น Private หรือแก้
Network จริงต้องตรวจสอบผลกระทบต่อ Lambda, การเข้าถึงฐานข้อมูล, สิทธิ์ AWS Academy
และแผน deploy ก่อน ห้ามเปลี่ยนค่าโดยไม่ทดสอบการเชื่อมต่อ

### Out of Scope / Next Version

-   หลายสถานประกอบการภายในแผนเดียว หรือระบบสมัครหลายแห่ง/จัดอันดับตัวเลือก
-   การสร้าง Workflow หลาย Period แบบใหม่ นอกเหนือจากความสามารถที่ V3 มี
-   การเพิ่ม Status Model ใหม่หรือ Workflow หลังอนุมัติที่ยังไม่มี Requirement ชัดเจน
-   ระบบสร้าง/แก้ไข/มอบหมาย Deadline แบบเต็มรูปแบบ
-   การแจ้งเตือนอัตโนมัติผ่าน Email/SMS/บริการภายนอก
-   Full Audit Log ที่ครอบคลุมทุก field และทุกกิจกรรม
-   Dashboard/Analytics ขั้นสูง, SLA/uptime guarantee, load test ขนาดใหญ่
    หรือระบบ disaster recovery เต็มรูปแบบ
-   การสร้าง Login, Authentication, RBAC หรือ Workflow หลักของ V3 ใหม่ทั้งหมด
-   **Real User Validation:** การทดสอบกับผู้ใช้จริงอย่างน้อย 3 บทบาท (Student,
    Advisor, Coop Staff) ให้แยกเป็นงาน Next Version หากเวลา V4 ไม่เพียงพอ

## 4. Existing System & Architecture

### 4.1 Existing V3 Architecture

องค์ประกอบหลักของ V3 ตามสถาปัตยกรรมโครงการ ได้แก่

-   **Frontend:** React และ TypeScript
-   **Authentication:** Amazon Cognito
-   **API:** Amazon API Gateway
-   **Backend:** AWS Lambda
-   **Database:** PostgreSQL บน Amazon RDS
-   **Authorization:** ตรวจสอบ Role และเงื่อนไขการเข้าถึงในระบบ

รายการนี้อธิบายสถาปัตยกรรมที่โครงการใช้ ไม่ได้ยืนยันว่าการตั้งค่า AWS
ทุกส่วนในสภาพแวดล้อมที่กำลังใช้งานเป็นไปตามเป้าหมายด้านความปลอดภัยแล้ว ต้องตรวจสอบโค้ด
Terraform และค่าจริงใน AWS ก่อนสรุป

### 4.2 V4 Proposed Integration

V4 จะต่อยอดระบบเดิมตามความจำเป็น โดยมีแนวทางดังนี้

-   **Frontend:** เพิ่ม/ปรับหน้าสถานะ รายละเอียดแผน การส่งกลับแก้ไข และ Deadline
    display
-   **API / Backend:** ใช้ API เดิมก่อน เพิ่มหรือแก้เฉพาะ endpoint ที่จำเป็น
    พร้อมตรวจสอบสิทธิ์และสถานะฝั่ง Backend
-   **Database:** ใช้ Schema เดิมก่อน การเพิ่มตารางหรือ field
    ต้องมีเหตุผลและผ่านการตรวจสอบผลกระทบ
-   **Authorization:** ใช้ Cognito และ Role/assignment rules เดิม ไม่สร้าง
    RBAC ใหม่
-   **Reliability:** ตรวจสอบ validation, duplicate actions, concurrency
    และ error handling

### 4.3 Network Architecture Deliverable

ต้องจัดทำภาพแสดงองค์ประกอบและเส้นทางการเชื่อมต่อที่ตรวจสอบได้ ได้แก่

-   VPC และ Subnets ที่เกี่ยวข้อง
-   Route Tables และ Internet/NAT Gateway (ถ้ามี)
-   Security Groups และกฎ Inbound/Outbound ที่เกี่ยวข้อง
-   Lambda ว่าเชื่อมต่อ VPC หรือไม่ และอยู่ Subnet/Security Group ใด
-   RDS Subnet Group, Publicly Accessible และ Security Group
-   เส้นทาง Frontend → API Gateway → Lambda → RDS

ในเอกสาร/หลักฐานให้แยก 2 ส่วน: 1. **Current State:** ค่าที่ตรวจสอบได้จริงจาก
Terraform/AWS 2. **Recommended Target State:** ข้อเสนอ เช่น จำกัด RDS
ให้เข้าถึงจาก Lambda หรือแหล่งที่จำเป็นเท่านั้น

หาก AWS Academy ไม่อนุญาตให้ตรวจสอบหรือแก้ไขบางส่วน ให้บันทึกข้อจำกัดและหลักฐาน
error แทนการสรุปเองว่าได้ตั้งค่าแล้ว

## 5. User Scenarios & Acceptance Testing

TC1 และ TC2 เป็น Acceptance Scenarios หลักของ V4

### 5.1 TC1: Advisor Review & Student Resubmission

**Scenario:** อาจารย์ที่ปรึกษาที่ได้รับมอบหมายตรวจสอบแผน ส่งกลับให้นักศึกษาแก้ไข
และตรวจสอบแผนที่ส่งใหม่

**Steps** 1. Advisor เข้าสู่ระบบด้วยบัญชีที่มีสิทธิ์ 2.
ค้นหาแผนของนักศึกษาที่ตนได้รับมอบหมาย 3. เปิดดูรายละเอียดแผน 4.
ส่งแผนกลับให้นักศึกษาแก้ไขพร้อมระบุเหตุผล/ความคิดเห็น 5. Student
เข้าสู่ระบบและอ่านความคิดเห็น 6. Student แก้ไขข้อมูลและส่งแผนอีกครั้ง 7. Advisor
เปิดแผนเดิมและตรวจสอบว่ากลับเข้าสู่กระบวนการพิจารณาได้

**Expected Result** - Advisor พบและเปิดดูแผนของนักศึกษาที่ได้รับมอบหมายได้ -
Advisor ไม่สามารถพิจารณาแผนของนักศึกษาที่ไม่ได้รับมอบหมาย -
การส่งกลับต้องมีเหตุผลตามกติกา V3 - Student
แก้ไขและส่งแผนเดิมกลับเข้ากระบวนการได้ตาม Workflow V3 -
สถานะหลังส่งกลับและส่งใหม่ถูกต้องตาม State Model เดิม - หากมี Activity History
ให้แสดงเฉพาะเหตุการณ์/ผู้ดำเนินการ/เวลาที่มีข้อมูลจริง

### 5.2 TC2: Student Creates and Tracks a Plan

**Scenario:** นักศึกษาค้นหาสถานประกอบการและ Period สร้างแผนของตนเอง
ส่งให้อาจารย์ตรวจสอบ และติดตามสถานะ

**Steps** 1. Student เข้าสู่ระบบ 2. ค้นหาสถานประกอบการและตำแหน่งงานที่ระบบรองรับ
3. เลือก Period ที่มีอยู่ในระบบ 4. สร้างแผนของตนเอง
โดยเลือกหนึ่งสถานประกอบการต่อหนึ่งแผน 5. ตรวจสอบข้อมูลและส่งแผนให้อาจารย์ที่ปรึกษา 6.
เปิดหน้ารายการ/รายละเอียดแผนเพื่อติดตามสถานะ

**Expected Result** - Student ค้นหาสถานประกอบการ/ตำแหน่งและ Period
ที่มีอยู่ได้ - Student สร้างแผนของตนเองได้ โดยข้อมูลเชื่อมโยงกับ Period
และสถานประกอบการถูกต้อง - ระบบป้องกันแผนที่ซ้ำตามกติกา V3 - Student
ส่งแผนเพื่อพิจารณาได้ตาม Workflow V3 - ระบบแสดงสถานะล่าสุดที่ตรงกับข้อมูล Backend

  REL3: Duplicate Action  ส่งคำขอเดิมซ้ำ เช่น submit/review ซ้ำ               ระบบไม่สร้างผลซ้ำหรือทำให้ข้อมูลไม่สอดคล้อง

  REL4: Backend/API Error จำลองหรือทดสอบข้อผิดพลาดที่ควบคุมได้                  แสดง error ที่เหมาะสม ไม่เปิดเผย secret
                                                                         และไม่บันทึกข้อมูลครึ่งทาง

  REL5: Database          ทดสอบในสภาพแวดล้อมทดสอบที่ปลอดภัยเมื่อ DB ใช้งานไม่ได้  ระบบตอบข้อผิดพลาดอย่างควบคุมได้ และไม่รายงานว่าบันทึกสำเร็จ
  Unavailable

  REL6: History           เปรียบเทียบเหตุการณ์ที่แสดงกับการเปลี่ยนแปลงที่เกิดขึ้นจริง   แสดงเฉพาะข้อมูลที่มีหลักฐานและไม่สร้างประวัติที่ไม่ตรงกับข้อมูลจริง
  Consistency
  ---------------------------------------------------------------------------------------------------------------------------

REL5 ทำเฉพาะเมื่อมีสภาพแวดล้อมที่ปลอดภัยและได้รับอนุญาต หากทำไม่ได้ให้ระบุ Not Run
พร้อมเหตุผล ห้ามทำให้ฐานข้อมูล/ระบบที่ใช้งานจริงหยุดทำงานเพื่อทดสอบ

## 6. Proposed Issue Breakdown

รายการต่อไปนี้เป็นข้อเสนอสำหรับแบ่งงาน V4 ให้สอดคล้องกับเวลาและขอบเขตที่เลือก
ต้องกำหนดผู้รับผิดชอบและ dependency ร่วมกันก่อนเริ่มงาน

### V4-01: Student Plan Flow & Status Tracking

**Scope** - ทำ TC2 ตั้งแต่ค้นหา Employer/Position และ Period
ไปจนถึงสร้าง/ส่งแผนและติดตามสถานะ - ใช้หนึ่ง Employer ต่อหนึ่ง Plan และ Period ที่
V3 มีอยู่ - รักษากติกาการสร้างแผนและ State Model ของ V3

**Acceptance Criteria** - TC2 ผ่านตาม Expected Result - ข้อมูล
Employer/Period/Student เชื่อมโยงถูกต้อง - ไม่มีแผนซ้ำตามกติกา V3

**Out of Scope:** หลาย Employer ต่อหนึ่ง Plan, ระบบ Period ใหม่, Status
Model ใหม่

### V4-02: Advisor Review & Resubmission

**Scope** - ทำ TC1 สำหรับ Advisor ที่ได้รับมอบหมาย -
รองรับการส่งกลับพร้อมเหตุผลและการส่งใหม่โดย Student -
แสดงสถานะและความคิดเห็นที่จำเป็น

**Acceptance Criteria** - TC1 ผ่านตาม Expected Result - ตรวจสอบ
assignment และสิทธิ์ฝั่ง Backend - การส่งกลับ/ส่งใหม่ไม่ทำให้ Workflow V3 เสียหาย

**Out of Scope:** Workflow หลังอนุมัติใหม่ หรือการเปลี่ยนสิทธิ์/สถานะโดยไม่มี
Requirement

### V4-03: Deadline Display & Limited Activity History

**Scope** - ตรวจสอบแหล่งข้อมูล Deadline ที่มีอยู่และแสดงผลเท่าที่รองรับ -
ตรวจสอบข้อมูล Activity History ที่มีอยู่ - หากทำได้ ให้แสดงเหตุการณ์สำคัญที่เกี่ยวข้องกับ
TC1 โดยไม่อ้างว่าเป็น Full Audit Log

**Acceptance Criteria** - แหล่งข้อมูล Deadline
ระบุได้และค่าที่แสดงตรงกับแหล่งข้อมูล - ประวัติที่แสดงมีหลักฐานจากข้อมูลจริง -
หากข้อมูลไม่พร้อม ต้องบันทึกข้อจำกัดแทนการสร้างข้อมูลสมมติ

**Out of Scope:** Deadline management, automated notifications, Full
Audit Log

### V4-04: Reliability & Regression Testing

**Scope** - ทดสอบ TC1, TC2, RT1--RT5 และ REL1--REL6
ตามสภาพแวดล้อมที่อนุญาต - ตรวจสอบ API response และ data integrity - บันทึกผล
Pass/Fail/Not Run พร้อมหลักฐาน

**Acceptance Criteria** - ทุกกรณีมีผลทดสอบหรือเหตุผลที่ไม่ได้ทดสอบ - RT1--RT5
ยืนยันกติกา V3 - ไม่กล่าวอ้างว่าผ่านหากไม่มีผลทดสอบจริง

**Out of Scope:** SLA guarantee, large-scale load test, full disaster
recovery

### V4-05: AWS RDS Networking Review & Architecture

**Scope** - ตรวจสอบ Current State จาก Terraform/AWS - ทำ Network
Architecture Diagram แสดง Lambda/API/RDS และ Network Controls -
เปรียบเทียบ Current State กับ Recommended Target State -
ประเมินผลกระทบ/ข้อจำกัด AWS Academy ก่อนเสนอการเปลี่ยนแปลงจริง

**Acceptance Criteria** - Diagram ตรงกับหลักฐานที่ตรวจสอบได้ - ระบุค่า Publicly
Accessible, Subnets, Security Groups และ Lambda VPC setting
เท่าที่ตรวจสอบได้ - แยกข้อเท็จจริง ข้อเสนอ และข้อจำกัดอย่างชัดเจน - หากแก้ config จริง
ต้องทดสอบ Lambda-to-RDS และการ deploy หลังแก้

**Out of Scope:** เปลี่ยน Network โดยไม่ตรวจสอบ, เปิด DB ให้เข้าถึงจากทุก IP,
อ้างว่า Private แล้วโดยไม่มีหลักฐาน

## 8. Success Criteria

V4 จะถือว่าบรรลุเป้าหมายเมื่อมีหลักฐานยืนยันว่า

-   TC1 ผ่าน: Advisor ตรวจแผนที่ได้รับมอบหมาย ส่งกลับพร้อมเหตุผล และ Student
    ส่งแผนเดิมกลับเข้าพิจารณาได้
-   TC2 ผ่าน: Student ค้นหา Employer/Period สร้างแผนหนึ่ง Employer ต่อหนึ่ง Plan
    ส่งแผน และติดตามสถานะได้
-   RT1--RT5 ผ่านตาม Expected Result หรือมีการบันทึกผล Fail/Not Run
    พร้อมเหตุผลและแนวทางแก้
-   REL1--REL6 มีผลทดสอบตามที่ทำได้อย่างปลอดภัย และระบุ Not Run
    สำหรับกรณีที่ไม่มีสภาพแวดล้อมรองรับ
-   Deadline display แสดงค่าจากแหล่งข้อมูลจริง
    หรือระบุชัดเจนว่าไม่มีแหล่งข้อมูลพร้อมใช้งาน
-   Activity History แสดงเฉพาะข้อมูลที่ตรวจสอบย้อนกลับได้ หรือบันทึกข้อจำกัด
-   Network Diagram แยก Current State กับ Recommended Target State
    และมีหลักฐานสนับสนุน
-   ความสามารถและ Workflow เดิมของ V3 ที่เกี่ยวข้องยังทำงานได้
-   มีหลักฐานการทดสอบที่ตรวจสอบย้อนหลังได้ โดยไม่ระบุ Pass หากยังไม่ได้ทดสอบ

## 9. Development Constraints

-   กำหนดส่งงาน 2/11; จัดลำดับให้ TC1, TC2 และ Regression ที่สำคัญมาก่อน
-   พัฒนาต่อยอดจาก V3 และหลีกเลี่ยงการเขียน Authentication, Authorization หรือ
    Workflow ใหม่
-   ไม่เพิ่ม Status Model, Employer relationship หรือ Period workflow
    ใหม่โดยไม่มีข้อตกลงจากทีม
-   ใช้หนึ่ง Employer ต่อหนึ่ง Plan, Period เดิมของ V3 และ Deadline display
    only ตามแนวทางเบื้องต้น
-   ตรวจสอบโค้ด API, Schema, Terraform และ AWS configuration ก่อนแก้ไข
-   การเปลี่ยน RDS networking ต้องประเมินผลกระทบต่อ Lambda, การเข้าถึงฐานข้อมูล
    และข้อจำกัด AWS Academy ก่อนเสมอ
-   ทุก Issue ต้องมี Acceptance Criteria และหลักฐานการทดสอบ
-   แยก Current State, Proposed Change, Verified Result และ Not Run
    ให้ชัดเจน
-   ไม่กล่าวอ้างว่าระบบมีความพร้อมใช้งานหรือความปลอดภัยระดับใด หากไม่มีหลักฐานรองรับ
